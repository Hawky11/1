# Stage102 — три реальных 0x27, 15 отклонений

В оригинальном AALib.exe (SHA256 `28cd69a7b6219ff0fa101ecebfcbe98962dc3f391b522d1fd6e32c006cf855ba`) проверена внутренняя логика F34D0/F30B0. В существующем живом Stage98 r2 сеансе нашли **3 естественных изменения FFFFFFFF→0x27** на Stage96 F79B6 (другая ветка вызова F34D0, не class5). Три цепочки `975→976→977→806→608→209`, `6076→6077→6078→4630→4085→612`, `15102→15103→15104→11658→10356→1468`: результат сохранился через остальные writer-узлы и Stage95 bypass, но на Stage94 все три получили **ECX=0**, native gate отклонил FinalCommand.

В общей Stage94 выборке **15 ESI=0x27 gate**: 12 из F3930 producer и 3 из bypass, все 15 отклонены. Из 167 исходных FinalCommand ни один не имел payload 0x27. В class5 (461 наблюдений) 0x27 не создавался, но статическая таблица action0/action0x22 **обе содержат 0x27**. Следовательно, причина отрицательного class5 — какая-то из **других динамических проверок**, но без дополнительных значений нельзя назвать точно какую.

Архив Stage102 из этого чата: `tools/verify_stage102.py`, `tools/test_stage102.py`, полный отчёт, JSON. Проверка оригинального EXE **35/35 PASS**, офлайн-тесты **19/19 PASS**. Ни DLL, ни игровых изменений. Stage36 OFF.

Следующая задача Stage103: исследовать, откуда в F7B0A берётся **ECX=0** при выбранном ESI=0x27. Не форсировать ECX или команду в игре.
