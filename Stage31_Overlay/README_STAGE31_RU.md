## Установка и прогон

1. Скопировать `Stage31_Overlay/src/AIQueueTrace.cpp` в `D:\INCUBATOR\ArcanaAIOverhaul\src\AIQueueTrace.cpp`.
2. Скопировать `Stage31_Overlay/ArcanaAI.ini` в корень проекта. **Сохранить Stage29 `src/AITrace.cpp` и остальные исходники.**
3. Выполнить обычный x86 `Build.bat`. Сохранить полный `Build.log`.
4. Установить полученный `dinput8.dll` и обновлённый INI привычным способом. Перед новым запуском перенести старые runtime-логи в отдельную папку архива, чтобы новый прогон не смешался со старым.
5. Запустить естественный COM-vs-COM, дать пройти нескольким эпизодам. После последнего интересующего события оставить игру работающей ещё минимум 2 секунды для выгрузки буфера.
6. Загрузить `Build.log` и все свежие runtime-логи. Особенно нужны `ArcanaAI_Stage31AlternatePathTrace.log`, `ArcanaAI_Stage29Bit17Transitions.log`, `ArcanaAI_ProducerCallTrace.log`, `ArcanaAI_QueueTrace.log`, `ArcanaAI_EventDispatchTrace.log`.

Ожидаемые строки в новом журнале:

```
STAGE31_ALTERNATE_PATH_BUILD=2026-11-09-r1
STAGE31_CONFIG enabled=1 ...
Installed Stage31 ... callsite RVA 0x000F6A8C -> helper RVA 0x00130A10 ...
```

Один лишь маркер означает наличие кода в DLL. Установку подтверждает отдельная строка `Installed Stage31`. При несовпадении сигнатур выводится ERROR, новый хук не ставится. Stage31 требует установленный существующий queue observer; без него альтернативный хук не устанавливается.

## Что наблюдаем

- Пассивная замена только пятибайтного CALL `F6A8C -> 130A10`. Аргумент snapshot передаётся оригинальной функции ровно один раз. Возврат вызывающей стороны и её аргументы сохраняются.
- `kind=1` — BEGIN, `kind=2` — END. Общие `episode`, поток, игрок, QPC и маска читаемости связывают снимки.
- `kind=3` — отдельный вызов очереди типа0 с return RVA `156E4C`, до/после оригинального queue helper. Фильтр не требует старого `EnableCpuQueueDetailTrace`, не объединяет события и не меняет существующую запись типа1.
- У вложенной записи `episode` равен текущему родительскому вызову на том же потоке. `episode=0` означает отсутствие отслеживаемого родителя, а не подтверждённую связь с ближайшим BEGIN. Сохраняются и такие записи для сравнения.
- Вложенность учитывается до 8 уровней. При превышении вложенные события не приписываются внешнему вызову, выводится предупреждение. Кольцевой буфер — 1024 записи, выгрузка существующим worker раз в 1000 мс. Переполнение увеличивает `dropped` и создаёт разрыв `seq`.
- Форматирование и запись файла выполняются на worker. На игровом потоке остаются безопасные чтения, QPC и краткая блокировка буфера.

## Поля журнала

`qpc` — начало соответствующего снимка; для kind3 `qpcAfter` — отметка после исходного queue helper. `side` определяется по точному адресу P1/P2; `parent` у BEGIN/END обозначает внешний episode, у kind3 — текущий episode. При kind3 `player` — получатель очереди, `values[0]` — игрок родительского scope, если он известен. Это позволяет заметить переход между игроками.

У kind1/2 `values` — 32 сырых DWORD. Бит N в `mask` подтверждает чтение значения N; ноль без установленного бита не является наблюдённым нулём. Числа с плавающей точкой хранятся как исходные биты, без вычислений на игровом потоке.

| Индекс | Значение |
|---|---|
| 0–3 | четыре DWORD структуры snapshot |
| 4 | P+3B84, включая bit16/17/19/20/21 |
| 5 | P+3B80 |
| 6–7 | P+3978, P+3F20 |
| 8–9 | P+4238, P+423C |
| 10–12 | DWORD P+3A2C, P+3A30, P+3A34: сырое состояние mailbox/tuple |
| 13 | P+3B20: slot0x38 массива P+3A3C |
| 14–16 | P+3ED0, P+3ED4, P+3EDC |
| 17–19 | P+3B70, P+3F34, P+3F30 |
| 20 | текущий O=[P+4] |
| 21–27 | O+1C, O+20, O+24, O+290, O+150, O+154, O+1E4 |
| 28 | адрес локального кандидата state block P+3978 |
| 29–31 | DWORD этого кандидата +20, +24, +34 |

Для kind3 `before/after=(guard,active,storedType,storedPayload)`, с отдельными `beforeReadable/afterReadable`. Наличие записи доказывает вызов; результат приёма нужно оценивать по исходному queue helper и значениям полей. Если те же значения были до вызова, их совпадение после не доказывает новую запись само по себе.

**Индексы28–31 не объявляются результатом E6960:** у особого состояния возможна переадресация. Наблюдатель намеренно не вызывает игровые функции для вычисления адреса. Для такой ситуации потребуется отдельное наблюдение фактического возврата E6960. `EAX/AL` после 130A10 не трактуются как success: известный caller сам выставляет AL1.

## Проверка реализации

- `tools/verify_stage31.py --binary <AALib.exe>`: SHA256, четыре набора байтов непосредственно из исходника, обе цели E8 и INI. Выполнено успешно на оригинальном EXE.
- `tools/test_records.py`: извлечённая C++ логика компилируется host g++ с mock Windows API. Проверены маски чтения, parent linkage, события без scope, фильтр return RVA, один вызов оригинала, глубина9, TLS в другом потоке и заполнение буфера. Это не проверка Windows API/ABI.
- `tools/test_wrapper.py`: GNU assembler собирает извлечённый asm, Unicorn 2.1.4 сравнивает прямой вызов и обёртку в 12 сочетаниях выравнивания/флагов, включая DF. Проверены аргумент, один вызов, GPR/EFLAGS, данные x87/XMM/MXCSR и неизменность caller-owned stack. Диагностические заглушки намеренно портят volatile registers и FP state.
- Особенность Unicorn: FIP/FDP после FXRSTOR не восстановлены эмулятором, поэтому диапазон метаданных FX image [8,24) исключён из этой проверки. Дополнительный тест полного нативного FX image **пропущен**: среда не исполняет IA32 ELF. Это ограничение проверки, не утверждение о результатах MSVC/игры.
- Обёртка использует PUSHFD/PUSHAD и выровненные FXSAVE/FXRSTOR до/после диагностических вызовов. FNINIT даёт диагностике пустой x87-стек, затем восстанавливается сохранённое состояние. YMM upper halves не входят в FXSAVE; проект следует собирать обычными прежними x86-флагами без /arch:AVX. Общая ABI-реализация старого QueueInsertHook остаётся прежней.

## Ограничения и критерий результата

Снимки нескольких полей не атомарны. Выход из игры может оборвать последние записи до выгрузки. TLS-scope предполагает нормальный возврат оригинального helper; исключение/longjmp через него может оставить незакрытый scope. Прогон с отсутствующим END, предупреждениями или ошибками нельзя считать доказательством отсутствия действия. Перезапуск игры сбрасывает scope и буферы.

Искомая цепочка: Stage29 set → Stage15 bit17=1 → Stage31 BEGIN → kind3 с тем же episode/потоком и корректным адресом очереди → Stage31 END → Stage29 clear. Если kind3 отсутствует при полном эпизоде без потерь, сначала сопоставить bit19/20/21, O+20 и специальные состояния из Stage30; не объявлять это автоматически ошибкой AI.

Исторические ветки не изменяются. Stage31 остаётся **source-only**, пока не получены успешный Build.log, установка хука и новый игровой журнал.
