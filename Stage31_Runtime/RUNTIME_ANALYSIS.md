## Полная матрица корреляции

QPC дельты измерены в тиках относительно Stage31 BEGIN (не миллисекунды). Для каждого эпизода последовательность:
`Stage29 bit17 0→1 (post-RVA FAD2) -> Stage15 F6A68 bit17=1, branchTaken=0 -> Stage31 BEGIN -> same-episode kind3 type0 payload0 -> Stage31 END -> Stage29 bit17 1→0 (post-RVA ED1A9)`.

| 1 | P2 | 1 / 2 | 890 | -2556 | -327 | +200 | +631 | +1187 |
| 2 | P1 | 3 / 4 | 6163 | -3098 | -386 | +229 | +697 | +1349 |

Во всех 6 BEGIN `values[4]=00020000`, END `values[4]=00030000`: внутри вызова появляется bit16 при сохраняющемся bit17. Stage29 фиксирует последующий сброс bit17 до `00010000`. Совпадает с ранее статически найденной альтернативной обработкой через `130A10/E6C60`; данный наблюдатель не перехватывает непосредственно инструкцию, поставившую bit16.

Для 6 вложенных вызовов queue `before=(0,0,65535,65535)` и `after=(0,0,0,0)`; guard=0, active=0 остаются неизменны, storedType/storedPayload становятся нулями. **Фактический вызов F2DE0 доказан, но активная команда/успешный эффект в игре этим не доказаны.** `QUEUЕ_EVENT result=ACCEPTED_BY_QUEUE` агрегированного старого лога — не эквивалент доказанного исполнения игровой команды.

## Контрольный прямой маршрут (тот же сеанс)

Седьмой Stage15 `F6A68`-эпизод у P1 при `bit17=0`: seq 1207, QPC 470771056321, `branchTaken=1` → `Stage13 ALT_CALLSITE` QPC 470771057003, type1 payload `0x1E` → `QueueTrace QUEUE_EVENT_DETAIL` QPC 470771057081, type1 payload `0x1E`, `activeBefore=0`, `activeAfter=1`, `storedAfter=(0001,001E)`. Далее Stage21 classifier AL0 при QPC 470771062817, fallback slot3 до/после =0. На этом прямом маршруте не наблюдается Stage31 BEGIN, как и ожидается.

Это контрпример гипотезе, будто наличие/отсутствие type1/0x1E объясняется принадлежностью к P1/P2: оба игрока проходят альтернативный маршрут при bit17=1, P1 в этой же сессии проходит прямой маршрут при bit17=0.

## Наблюдения по побочным полям и ограничения

- У всех 6 эпизодов `values[17]` (P+3B70): до `00000640` (первые пять) либо `00000440` (шестой), после `00020640` либо `00020440` соответственно.
- `values[10]` и `values[11]` (`P+3A2C/3A30`) изменяются `FFFF0000/0000FFFF -> 0/0` во всех 6 эпизодах. `values[30]` локального кандидата `P+3978` изменяется `00000064 -> FFFFFF38` во всех 6; **не** считать этот кандидат разрешённым возвращаемым объектом E6960.
- Внешние type0 (episode=0): P1 24, P2 22; payload распределение: P1 [0:13,1:7,4:4], P2 [0:18,1:2,5:2]. Связывать их с ближайшим BEGIN нельзя.
- Данные не доказывают дефект AI и не показывают наблюдаемую успешность/неуспешность атаки или движения. Снимки не атомарны, отсутствие WARN не гарантирует отсутствия потерь вне наблюдаемых потоков, выход из игры способен обрезать буфер. Внутриигровое сопоставление действия с конкретным вызовом не записано.
- Существующий EventDispatchTrace агрегирует type0 и не предоставляет того же per-event `episode`; без дополнительной инструментализации нельзя утверждать, что каждая из шести type0 записей была индивидуально передана dispatcher.

## Вывод и следующий шаг

**Stage31 runtime завершён для исследованного сценария.** Родитель `0x130A10` действительно порождает вложенный type0/payload0 вызов `F2DE0` для всех шести bit17=1 попыток; это нормальная ветвь оригинальной программы для данного состояния, а не доказательство потерянной type1/0x1E команды. Отдельная ветка с bit17=0 действительно генерирует type1/0x1E.

**Stage32:** сначала статически исследовать судьбу type0/payload0 при inactive=0 и смысл установки bit16, в частности связи с dispatch/потребителем, до новых runtime-хуков. Если статических данных недостаточно, сделать лишь узкий пассивный QPC-коррелированный observer на type0 dispatch и/или фактический state transition; не форсировать bit17, не вводить type1/0x1E и не менять gameplay до доказательства неисправности. Старые Stage-ветки и source-only Stage31 не переписывать.
