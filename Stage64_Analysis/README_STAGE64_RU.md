# Stage64 — откуда исходный движок берёт ID действия

**Статус: STATIC VERIFIED.** [Технический отчёт](STATIC_ANALYSIS.md). Проанализирован оригинальный AALib.exe из библиотеки (SHA-256 начинается 28cd69a7), без новой сборки мода и без запуска AH3.

## Что получилось

- Все 296 прямых вызовов общего setter E5BF0 подтверждены как реальные инструкции x86 CALL, а не просто совпадения байтов E8 внутри .text.
- Они сгруппированы в 201 область между инструкциями INT3. Это **техническая разбивка**, а не 201 доказанная функция ИИ.
- По ближайшим аргументам: 212 вызовов с константным flag=0, 12 с flag=1, 14 с динамическим флагом, 58 неразрешённых из-за ветвления или недостатка контекста.
- В 120 вызовах ID передаётся константой, в 118 из регистра, в 58 источник не установлен.
- Callback 12EB10 имеет 19 прямых переходов к 131CA0 и 11 к 131D00. Оба обработчика при выполнении своих условий могут вызвать E5BF0.
- Callback 123AF0 и 1DA490 обращаются к общему обработчику 1BD6E0. У него 34 прямых вызывающих участка; это ещё не доказательство, что каждый из них формирует запрос.
- У 158 из 202 активаций Stage42 нет совпавшего Stage39 action-output события. В 35 из этих 158 ID встречается среди статических констант, в остальных 123 — нет. Это только подсказка для дальнейшей диагностики, а не атрибуция к конкретному вызову.

## Повторная офлайн-проверка (не обязательна)

Скрипты [analyze_stage64.py](tools/analyze_stage64.py), [verify_stage64_callback_edges.py](tools/verify_stage64_callback_edges.py) и [test_stage64.py](tools/test_stage64.py) уже были проверены в текущей среде; основные две проверки оригинального EXE дали PASS, синтетические тесты аргументов 4/4 PASS.

Для воспроизведения требуется оригинальный AALib.exe и GNU objdump с Intel-синтаксисом. Пример PowerShell (явно указываем кодировку UTF-8, поскольку Windows PowerShell 5.1 по умолчанию может записывать текст иначе):

    $exe = "D:\PATH\TO\AALib.exe"
    $dis = "D:\PATH\TO\AALib_text_disasm.txt"
    objdump -d -M intel $exe | Out-File -Encoding utf8 $dis

    py -3 .\Stage64_Analysis\tools\analyze_stage64.py $exe --objdump $dis --json .\Stage64_sites.json
    py -3 .\Stage64_Analysis\tools\verify_stage64_callback_edges.py $exe --objdump $dis --json .\Stage64_edges.json
    py -3 .\Stage64_Analysis\tools\test_stage64.py

Не загружай полный дамп дизассемблирования или оригинальный EXE на публичный GitHub. JSON со списком RVA создаётся только локально.

## Следующий этап — Stage65

Нужен точечный **пассивный источник событий записи запроса P+3F4C**, предпочтительно общий E5BF0 с отдельной обработкой условного пути E9E30. Это новая диагностическая идея, а не уже собранная DLL.

Для нового hook сначала потребуется статическая проверка x86 ABI (ECX, два аргумента, RET 8), сохранения регистров/FPU, оригинальных байтов, совместимости с существующими Stage38/59 наблюдателями и нулевого вмешательства в игровой результат. Только после этого можно собирать и проверять DLL, а затем делать короткий COM-vs-COM. Нельзя принудительно ставить action ID, изменять приоритеты или координаты.

**На Stage64 ничего запускать и пересобирать не нужно.** Рабочая Stage59 r2 DLL (1 153 024 байта) остаётся эталоном.
