# Stage66 — нашли путь смены ожидающего ID и источник возможного нуля

**Статус:** оригинальные инструкции и CALL-переходы проверены. Это **СТАТИЧЕСКИЙ** этап: фактическое исполнение двух подозрительных веток в прежнем запуске пока не подтверждено. **Ничего собирать и загружать для Stage66 не требуется.**

[Полный технический отчёт](STATIC_ANALYSIS.md) · [Офлайн-проверка исходного EXE и старых логов](tools/verify_stage66.py).

## Два результата

**Два случая 0x2F → 0x25 (Stage42 seq39/155).** Последний Stage41 видел ожидающий ID 0x2F, но Stage42 уже активировал 0x25. Вызов из подтверждённого RVA AD75C попадает в функцию 1E9F40, которая **до точки наблюдения Stage42** проверяет флаг O+30, затем может перенести ID из O+68 в O+64 и очистить O+68. Это в точности воспроизводит видимую структуру состояний при условии, что на входе был отложен 0x25. **Входное O+68 пока не измерялось**, так что это объяснение остаётся кандидатом.

**Один запрос ID0 без Stage65 (Stage40 seq320).** В оригинальном E9E30 есть самостоятельная инструкция E9E60, которая при двух проверках может записать P+3F4C равным нулю. Источник — неизменённая в оригинальном EXE ячейка по адресу 008254E8 со значением 00000000. Stage65 наблюдает только E5BF0 и такую запись не увидел бы. **Вызов E9E60 именно в seq320 ещё не измерялся.**

Заодно исправлено потенциальное неверное чтение условия E9E30: его запись возможна только при **сброшенном**, а не установленном бите 15 P+3B7C и при ненулевом AL после F2ED0.

На ПК с Python 3 и оригинальным частным AALib.exe (НЕ dinput8.dll), находясь в клоне новой ветки:

Также можно добавить старые логи **строго одного запуска 11.11.2026 00:44–00:45**:

Для второго варианта нужны Stage65RequestOrigin, Stage40ActionConsumer, Stage41ObjectCommit, Stage42ActionActivation и Stage43ActivationOrigin логи. **Не смешивать запуски.** Оригинальный EXE остаётся локально и не загружается на публичный GitHub.

Оригинальный PE SHA256: 28cd69a7b6219ff0fa101ecebfcbe98962dc3f391b522d1fd6e32c006cf855ba. Здесь независимо проверены 21 машинная сигнатура, три оригинальных CALL и исходная глобальная константа 0. Полный опубликованный Python-скрипт не заявляется как испытанный на твоём Windows, он нужен для воспроизводимости.

## Stage67 — какой тест будет действительно полезен

Нужно **два узких пассивных наблюдения**, а не повторный анализ координат:

1. Снимок **до и после оригинального вызова AD75C→1E9F40**: O+30, O+64, O+68, O+08, игрок, TID и QPC. Это позволит отличить отложенный переход 0x25 от другого оригинального писателя O+64.
2. Если необходимо, снимок **самой оригинальной записи E9E60**, когда она записывает нулевой ID в P+3F4C, чтобы подтвердить или опровергнуть её связь с запросами без Stage65.

Сначала проверка ABI и совместимости с уже установленными хуками; только потом x86-сборка и один тест COM-vs-COM. **Не ставить новые DR watchpoints**, не менять значения ID/координат/AI и не отключать Stage59.

**Оставить рабочую Stage65 DLL размером 1 879 552 байта**, Stage59 r2 — 1 153 024 байта для отката. Новая DLL Stage66 не создавалась.
