# Stage67 — два пассивных наблюдателя оригинальных путей

**SOURCE ONLY, 2026-11-11.** Подготовлены исходники; Windows x86 DLL ещё не собрана и в игре не проверена. Оригинальный EXE повторно проверен по SHA-256. 512 сравнений извлечённого ассемблера обёрток с оригинальным путём в Unicorn прошли, включая сохранение GPR/FLAGS/ESP, непустого x87, XMM0–7 и MXCSR. Это не тест полного C++ обработчика или Windows API.

Ветка основана на Stage66 `748a0a61`; адаптер взят точно из Stage65 source `04ecb3370a66b4ed6dfd3d726df35f6f37546cc8`. В адаптер добавлены только include, установка Stage67 после Stage65 и сброс буфера Stage67 существующим потоком. `main` и предыдущие исходные/доказательные ветки не меняются.

## Что наблюдаем

1. **CALL AD75C → 1E9F40.** До и после исходного вызова сохраняются O+08, байт O+30, O+60, O+64, O+68, P/O/side/TID/QPC и EAX результата. Функция без стековых аргументов вызывается один раз. Оба исходных RET возвращаются через POST-наблюдение.
2. **MOV на E9E60.** Шестибайтная инструкция `MOV [ESI+3F4C],EDX` заменяется переходом в обёртку, выполняется там один раз с исходными регистрами и продолжается с E9E66. Сохраняются фактический EDX, запрос и флаги игрока до/после, а также текущее значение глобального источника. Ноль не подставляется: записывается именно исходный EDX, в том числе если он ненулевой.

Новых аппаратных breakpoint нет. Stage59 сохраняет DR0/DR1; Stage67 не читает и не записывает debug-регистры. ID, координаты и логика COM не подменяются. Дополнительные наблюдения всё же имеют временную стоимость; отсутствие влияния на производительность требует игрового теста.

При ERROR после записи патчей (`protect/cache`) захват считать недействительным, закрыть игру и вернуть сохранённую DLL.

Для анализа нового запуска нужны **Build.log + Stage67, Stage40, Stage41, Stage42, Stage43, Stage65 и Stage59** из одной сессии. Старые seq39/155/320 относятся только к прошлому запуску: номера в новом тесте будут другими.

## Важное изменение интерпретации Stage43

Внешний CALL теперь проходит через обёртку. Поэтому **сырой внешний адрес возврата Stage43 для AD75C будет внутри DLL**, а `knownCaller=0` ожидаем. Это не новый неизвестный вызывающий участок движка. Stage43 оставлен без подмены значений.

Для этого пути источник теперь устанавливается записью Stage67 kind=0 (`callerReturn=gameBase+AD761`) и вложенным Stage42 по одинаковым P/O/TID/side и QPC. Внутренний `nativeReturnRVA=1E9F67` Stage43 не меняется. Старые анализаторы, требующие `callerRVA=AD75C` в каждой Stage43-строке, **нельзя применять к этому запуску без адаптации**.

## Критерии подтверждения

**Перенос 2F → 25:** kind=0 PRE `v1!=0`, `v3=2F`, `v4=25`, маски `1F/1F`; внутри его интервала Stage42 PRE pending=25/deferred=FFFFFFFF, а затем active=25. POST Stage67 должен согласоваться с этим состоянием. Одного совпадения соседних строк или только POST недостаточно. Остальные допустимые переносы фиксировать отдельно от именно 2F→25.

**Запрос нуля:** kind=1 `writeValue=0`, PRE/POST маски `07/07`, POST `v0=0`. Это доказывает исполнение отдельной записи. Для связи с потреблением требуется следующий Stage40 того же P/side/TID с PRE request=0 после writer POST, без промежуточного наблюдаемого writer Stage65/Stage67 или потребления Stage40. Даже тогда формулировка — непротиворечивая наблюдаемая цепочка; неизвестные неперехваченные записи полностью не исключены.
