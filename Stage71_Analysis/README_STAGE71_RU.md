# Stage71 — найден нативный источник селектора `P+3F50=1`

**11.11.2026. Статический механизм подтверждён; runtime EIP конкретной записи селектора НЕ наблюдался.** [Полный технический отчёт](STATIC_ANALYSIS.md) · [верификатор оригинального EXE](tools/verify_stage71.py).

Исследован оригинальный `AALib.exe`, SHA-256 `28cd69a7b6219ff0fa101ecebfcbe98962dc3f391b522d1fd6e32c006cf855ba`, без модификаций. Stage70 r2 уже подтвердил, что в рабочем запуске на P1 селектор был **1**, а оригинальная инструкция `156787` записала deferred `25`, после запроса `2F`.

## 1. Конкретная функция, которая устанавливает селектор 1

```asm
AALib+155B79   mov edi,[ebp+08]
AALib+155B7C   mov esi,[edi]                   ; P — игрок
AALib+155B7E   mov eax,[esi+04]                ; O — объект
...
AALib+155D1D   mov dword ptr [esi+3F54],4     ; успешная ветка A
AALib+155D27   push 21h                        ; код события
AALib+155D29   mov dword ptr [esi+3F50],1     ; селектор = 1
AALib+155D3C   call AALib+0F2DE0              ; обработчик события
...
AALib+155D74   mov dword ptr [esi+3F54],3     ; успешная ветка B
AALib+155D7E   jmp AALib+155D27               ; туда же
```

**Обе успешные ветки записывают `P+3F50=1`.** Дополнительно меняется поле состояния `P+3F54` на `3` либо `4`; вызывается нативный обработчик с кодом `0x21`. Что именно означает это событие внутри игры, пока не доказано.

Эту функцию `AALib+155B70` вызывают **два оригинальных callback**:

```asm
AALib+1566F0   call AALib+155B70
AALib+1566FA   jne  AALib+156728   ; при успехе выйти из callback

AALib+1560B9   call AALib+155B70
AALib+1560C3   jne  AALib+156110   ; при успехе выйти
```

Первый callback — тот же `AALib+1566B0`, в котором в предыдущем этапе найдена цепочка запроса действия `156769` и deferred-записи `156787`. **Важная деталь:** после успешного установки селектора callback выходит досрочно. Значит, нельзя утверждать, будто он установил `1` и немедленно пошёл в `156769` **в рамках того же вызова**. Возможно, значение используется при следующем проходе callback.

## 2. Почему оригинальный движок выбирает эту ветку?

Перед записью селектора функция проверяет:

- бит 2 поля `P+3B78`;
- предикат оригинальной функции `0E86F0`;
- вещественные значения `O+80`, `O+88` и флаги `O+24`;
- доступность по `P+175` и индексированным байтам области `P+154`;
- условия из вспомогательных функций `125470` и `125490`.

Это доказанные обращения к памяти и условные ветвления. Семантику отдельных величин — например, «дистанция» или «приоритет атаки» — пока нельзя приписывать без дополнительного исследования.

## 3. Найдены и альтернативные пути изменения селектора

В исходной секции `.text` зафиксировано **20 прямых инструкций MOV, записывающих DWORD по смещению `+3F50`**:

| Тип записи | Количество |
|---|---:|
| Непосредственно константа `1` | **1** — `155D29` |
| Непосредственно константа `0` | 9 |
| Вычисленное значение регистра | 10 |

Некоторые из последних записывают `1` **или** `2`, например:

```asm
AALib+0F3DE9   mov [esi+3F50],ecx  ; ecx = 1 или 2
AALib+0F3E02   mov [esi+3F50],edx  ; edx = 1 или 2
```

**Поэтому найден не единственный возможный источник числа `1`, а единственный прямой `MOV [рег+3F50],1` в этом наборе.** Косвенные записи, копирование структур и другие формы модификации этим перечнем не исключены.

## 4. Как это связано с доказательством Stage70?

В последнем захвате Stage70 r2 было:

- Stage65 seq319: оригинальный вызов `156769` запросил `2F`;
- Stage70 seq1: `P+3F50=1→1`, `O+68:FFFFFFFF→25`, EDX=`25`;
- Stage41 seq320: ожидающее действие `22→2F`;
- Stage67 seq4561 / Stage42 seq234: перенос и активация отложенного `25`.

Теперь известно, что оригинальный движок **сам содержит конкретную ветку, устанавливающую селектор `1`**. Однако Stage70 регистрировал это поле только при потреблении. Он **не записывал EIP его предыдущего изменения**, так что выбирать между `155D29` и десятью register-derived writer на основании одного захвата нельзя.
