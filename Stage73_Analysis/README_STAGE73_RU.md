# Stage73 — откуда реально может появиться селектор 1

**11 ноября 2026. STATIC VERIFIED.** Проверен оригинальный `AALib.exe` с тем же SHA-256, что в Stage71–72. Новая DLL не нужна, игровое поведение не менялось.

Из 20 прямых записей `P+3F50` девять устанавливают 0, одна (`155D29`) устанавливает константу 1, ещё **десять** рассчитывают 1 либо 2 из результата проверки `AL`. Пять используют `1+(AL!=0)` — для 1 нужен `AL=0`; другие пять используют `1+(AL==0)` — для 1 нужен `AL!=0`.

Полный поиск инструкций `CALL rel32` с целью `155B70` в оригинальной `.text` нашёл только **`1560B9` и `1566F0`**. При входе `1566B0` в ветку `1566F0→155B70` этот вызов завершается возвратом из `1566B0` и при успехе, и при неуспехе проверки. Значит, при Stage38 seq4116, когда внутри `1566B0` уже доказаны непосредственный запрос `2F` и отложенная запись `25`, этот же вызов **не мог одновременно выполнить `155B70`**.

Если селектор установила именно инструкция `155D29`, это произошло до Stage38 seq4116. Повторные прежние вызовы `1566B0` (seq4092–4114) — кандидаты, но **не доказательство**. Значение 1 могло появиться и от одной из десяти других инструкций; лог Stage70 показывает значение в момент использования, а не адрес предыдущего writer.

**Следующее решение:** нужен ли отдельный реальный тест для поиска writer IP. Stage59 уже использует DR0/DR1, DR2/DR3 могут принадлежать другим наблюдателям. До проверки владельцев регистров и обработчиков исключений новый аппаратный breakpoint ставить нельзя. Одна проверка `155D29` недостаточна для отрицательного доказательства. Рабочую DLL Stage70 r2 (**1 892 864 байта**) оставить без изменений.
