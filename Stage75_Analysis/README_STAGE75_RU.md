# Stage75 — найден путь передачи события 0x11 в callback

**11 ноября 2026. STATIC VERIFIED.** Анализ оригинального `AALib.exe` (SHA-256 совпал с эталоном), ранее подтверждённых Stage74 логов и нативных инструкций. **Новую DLL не собирали.** Ни исходное EXE, ни игровые значения, ни логика COM не изменялись.

## Что удалось установить

Ранее было известно, что при пяти изменениях селектора следующий callback — `158570`, а его параметр `P+3ED4=0x11`. Теперь установлено, **откуда этот аргумент может поступать в оригинальном коде**:

```text
Событие в записи игрока P+3A2C
  текущий режим: P+3A2E
  текущий код:   P+3A30
           │
           ▼ условное копирование (0F2E50)
  прошлый режим: P+3A34
  прошлый код:   P+3A36
           │
           ▼ EE5E0 → EE643 → 158E90
  P+3ED0 = callback 158570
  P+3ED4 = sign-extended P+3A36 (например 0x11)
           │
           ▼ позднее EE7BE CALL EDI
  callback 158570, switch key 0x11
           │
           ▼ условная ветка 158ADC
  ЧИТАЕТ P+3F50 (селектор 0, 1 или 2)
```

**Ключевая находка:** `158E90` читает 16-битный код события из `P+3A36` и передаёт его в `0F7E70`, который только записывает адрес callback `158570` и параметр в `P+3ED0/P+3ED4`. В оригинальной секции `.text` найден один прямой `CALL 158E90` — `EE643`.

Ветка `EE643` доступна при обработке события, если его прежний режим `P+3A34=0` и соответствующие проверки записи проходят. При другом режиме вызываются другие функции. Само значение `0x11` в этом маршруте — **код события**, а не селектор `1`.

## Почему Stage74 показал изменение между callback

Оригинальная функция цикла после `EE7BE CALL EDI` продолжает работу: `EE7C7` вызывает очистку `FC60`, затем `EE7D1→EE480`, `EE7D6→E8DA0`, а при установленном бите 23 поля `P+3B7C` — `EE7EA→EE5E0`. В последнем пути возможна регистрация callback через `158E90`.

Stage38 снимал состояние **до** этой части обработки. Поэтому регистрация нового callback могла произойти между его POST одного кадра и PRE следующего. Это подтверждённая структура кода, **но точный EIP её исполнения в тех пяти переходах не записывался**.

## Что пока не найдено

Источник **`P+3F50=0/1/2`** остаётся неизвестным. Исходный callback с параметром `0x11` при прохождении проверки флага может **читать** селектор в `158ADC`, но это не инструкция записи.

Все 11 кандидатов Stage71/73 (одна прямая запись 1 и десять вычисляемых 1/2) остаются возможными; также не исключены косвенные записи. Мы **не подменяем код события, селектор или действия персонажа**.

## Дальше — Stage76

Следующий разумный диагностический этап — наблюдение промежутка **после** `FC60` и **до/после** `EE480`, `E8DA0` и условного `EE5E0`. Это позволит понять, внутри какого участка реально происходит изменение `P+3F50`, прежде чем пытаться ловить точный writer IP. Сначала проверка точек и ABI, затем только при необходимости пассивный исходник; не использовать занятые аппаратные DR0/DR1 и не занимать DR2/DR3 без аудита.
